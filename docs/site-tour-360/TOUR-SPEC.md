## 1. โจทย์

พนักงานสแกนไซต์งานเป็นระยะ → ได้ทัวร์ที่ **เดินไปมาระหว่างห้องได้เหมือน Google Street View**
และ **ย้อนดูเวอร์ชันเก่าได้ทุกเวอร์ชัน** (ก่อนโพรเทค / หลังโพรเทค / ติดตั้ง 30% / ฯลฯ)

**คุณค่าที่แท้จริง** ไม่ใช่ภาพ 360 สวยๆ แต่คือ **หลักฐานสภาพหน้างาน ณ เวลาหนึ่ง ที่จุดเดิมทุกครั้ง**
→ ใช้เคลมงาน · เถียงกับผู้รับเหมา · ทวนความจำก่อนเข้าไซต์ · (เฟสหลัง) อวดเจ้าบ้าน/ทำมาร์เก็ตติ้ง

## 2. คำศัพท์ (ใช้คำเหล่านี้ให้ตรงกันทั้งระบบ ทั้ง UI ทั้งโค้ด)

| คำ | หมายถึง | เปรียบเหมือน |
|---|---|---|
| **แผนผัง** (plan) | รูปแปลนพื้น 1 รูป ต่อ 1 ชั้น | แผนที่ห้างที่แขวนไว้ |
| **จุด** (point) | ตำแหน่งถ่ายคงที่ + ชื่อ + พิกัดบนแผนผัง | หมุด "คุณอยู่ตรงนี้" |
| **ลูกศร** (link) | ทางเดินจากจุด A ไปจุด B + ทิศเป็นองศา | ป้ายบอกทางที่ทางแยก |
| **เวอร์ชัน** (version) | การกลับไปถ่ายทุกจุดอีกครั้ง 1 รอบ + ชื่อ + วันที่ | เล่มอัลบั้มประจำรอบ |
| **ภาพ** (shot) | รูป 1 ใบ = 1 จุด × 1 เวอร์ชัน | รูปในอัลบั้ม |
| **หมุดคอมเมนต์** (pin) | จุดที่แตะไว้บนภาพ ผูก F-XX / QC / ข้อความ | โพสต์อิทแปะบนรูป |

> ⚠️ ห้ามใช้คำว่า "รอบสแกน" — เจ้าของงานเคาะให้ใช้คำว่า **"เวอร์ชัน"**
> ⚠️ ห้ามใช้คำว่า "ก่อสร้าง" ทั้งระบบ — ธุรกิจนี้คือ **งานบิ้วอิน**

## 3. กฎทอง 6 ข้อ (ผิดข้อใดข้อหนึ่ง = ฟีเจอร์พัง)

1. **จุด + ลูกศร + แผนผัง เป็นสมบัติของ "โครงการ" ไม่ใช่ของเวอร์ชัน**
   วางครั้งเดียวตอนเปิดโครงการ ใช้ยาวตลอด → รอบถัดไปพนักงาน **แค่ถ่ายทับจุดเดิม ไม่ต้องแตะลูกศรเลย**
2. **อัปเวอร์ชันใหม่ = เพิ่มชั้นใหม่ ไม่ใช่เขียนทับ** ของเก่าอยู่ครบตลอดไป คนละโฟลเดอร์ คนละแถวในฐานข้อมูล
3. **เข้าหน้ามาครั้งแรก = เวอร์ชันล่าสุดที่เผยแพร่แล้วเสมอ** ผู้ใช้ไม่ต้องเลือกอะไรก่อน
4. **เปลี่ยนเวอร์ชันแล้วต้องยืนอยู่ห้องเดิม** ห้ามเด้งกลับจุดแรก (นี่คือกลไกเทียบก่อน-หลังตัวจริง)
5. **เวอร์ชันที่ยังถ่ายไม่ครบ ห้ามโผล่ให้คนอื่นเห็น** ต้องกด "เผยแพร่" ก่อน
6. **ห้องที่เวอร์ชันนี้ยังไม่ถ่าย → แสดงภาพสำรอง พร้อมป้ายบอกตามตรงว่ามาจากเวอร์ชันไหน**
   ⚠️ **ภาพสำรองต้องมองย้อนหลังเท่านั้น** — เอาภาพล่าสุดของจุดนั้นที่ `captured_at` **เก่ากว่าหรือเท่ากับ** เวอร์ชันที่กำลังดู
   **ห้ามหยิบภาพจากเวอร์ชันที่ใหม่กว่ามาโชว์เด็ดขาด** (ไม่งั้นดูเวอร์ชัน "ก่อนโพรเทค" แล้วเห็นงานติดตั้งเสร็จ = หลักฐานเพี้ยน ใช้เคลมงานไม่ได้เลย)
   ถ้าย้อนหลังแล้วไม่มีภาพเลย (จุดเพิ่งถูกสร้างทีหลัง) → **จอว่างบอกตามตรง** "จุดนี้ยังไม่มีภาพในเวอร์ชันนี้หรือก่อนหน้า" + ปุ่มกลับจุดเริ่มต้น
   (ห้ามแอบเอาภาพเก่ามาโชว์เฉยๆ โดยไม่บอก — เดี๋ยวมีคนเข้าใจผิดว่างานเสร็จแล้ว)
7. **ห้ามปักหมุดคอมเมนต์ลงบนภาพสำรอง** — ปุ่มปักหมุดต้องเป็นสีเทากดไม่ได้ + บอกว่าให้ไปดูเวอร์ชันที่ถ่ายจริงก่อน พร้อมปุ่มลัดกระโดดไปเวอร์ชันนั้น
   (ไม่งั้นหมุดจะไม่รู้ว่าเป็นของเวอร์ชันไหน — ผูกกับเวอร์ชันปัจจุบันก็ผิดเพราะภาพเป็นของเก่า)

## 4. ฐานข้อมูล D1 — 6 ตารางใหม่

```sql
-- แผนผังพื้น (1 แถว = 1 ชั้น)
CREATE TABLE tour_plans (
  id TEXT PRIMARY KEY,              -- TP001
  project_id TEXT NOT NULL,
  floor_label TEXT NOT NULL,        -- "ชั้น 1"
  media_key TEXT NOT NULL,          -- คีย์ไฟล์ใน R2
  width INTEGER, height INTEGER,    -- พิกเซลจริง (ใช้คำนวณพิกัดหมุด)
  sort_order INTEGER DEFAULT 0,
  created_at INTEGER, created_by TEXT
);

-- จุดถ่าย
CREATE TABLE tour_points (
  id TEXT PRIMARY KEY,              -- TPT001
  project_id TEXT NOT NULL,
  plan_id TEXT,                     -- อยู่ชั้นไหน (ว่างได้ ถ้ายังไม่มีแปลน)
  name TEXT NOT NULL,               -- "ห้องนอนใหญ่ – มุมประตู"
  plan_x REAL, plan_y REAL,         -- 0..1 สัดส่วนบนแผนผัง (ไม่ใช่พิกเซล — จะได้ย่อขยายได้)
  sort_order INTEGER DEFAULT 0,     -- ลำดับที่พนักงานควรเดินถ่าย
  active INTEGER DEFAULT 1,
  created_at INTEGER, created_by TEXT
);

-- ลูกศรเดิน (ทางเดียว — ถ้าอยากเดินกลับได้ต้องมี 2 แถว)
CREATE TABLE tour_links (
  id TEXT PRIMARY KEY,              -- TL001
  project_id TEXT NOT NULL,
  from_point TEXT NOT NULL,
  to_point TEXT NOT NULL,
  yaw REAL NOT NULL,                -- องศา 0-360 ตำแหน่งลูกศรในภาพ
  pitch REAL DEFAULT -10,           -- องศา ก้ม/เงย (ลูกศรพื้นควรติดลบเล็กน้อย)
  label TEXT,                       -- ทับชื่อปลายทาง เช่น "ออกไประเบียง"
  created_at INTEGER
);

-- เวอร์ชัน
CREATE TABLE tour_versions (
  id TEXT PRIMARY KEY,              -- TV001
  project_id TEXT NOT NULL,
  name TEXT NOT NULL,               -- "หลังโพรเทค"
  note TEXT,
  status TEXT DEFAULT 'draft',      -- draft | published | trashed
  captured_at INTEGER,              -- วันที่ถ่าย (ผู้ใช้แก้ได้)
  published_at INTEGER,             -- วันที่กดเผยแพร่
  visibility TEXT DEFAULT 'internal', -- internal | client | public  ← เฟส 1 ใช้ internal อย่างเดียว
  created_at INTEGER, created_by TEXT,
  trashed_at INTEGER                -- ถังขยะ 30 วัน
);

-- ภาพ (1 จุด × 1 เวอร์ชัน = 1 แถว)
CREATE TABLE tour_shots (
  id TEXT PRIMARY KEY,              -- TS001
  project_id TEXT NOT NULL,
  version_id TEXT NOT NULL,
  point_id TEXT NOT NULL,
  media_key TEXT NOT NULL,
  kind TEXT NOT NULL,               -- sphere | pano | flat
  width INTEGER, height INTEGER,
  haov REAL, vaov REAL,             -- มุมมองแนวนอน/แนวตั้ง (องศา) — ใช้กับ pano
  yaw_offset REAL DEFAULT 0,        -- ค่าปรับหมุนให้ทับเวอร์ชันอื่นพอดี
  taken_at INTEGER,                 -- เวลาถ่ายจริงจากไฟล์ (EXIF) ถ้ามี
  uploaded_at INTEGER, uploaded_by TEXT,
  trashed_at INTEGER                -- ถ่ายทับ → ของเก่าลงถังขยะ 30 วัน
);

-- หมุดคอมเมนต์บนภาพ
CREATE TABLE tour_pins (
  id TEXT PRIMARY KEY,              -- TPN001
  project_id TEXT NOT NULL,
  point_id TEXT NOT NULL,
  version_id TEXT,                  -- ว่าง = ติดทุกเวอร์ชัน / ระบุ = เฉพาะเวอร์ชันนั้น
  yaw REAL NOT NULL, pitch REAL NOT NULL,
  kind TEXT NOT NULL,               -- note | ff | qc
  ref_id TEXT,                      -- รหัส F-XX หรือ id ผลตรวจ QC
  text TEXT,
  resolved INTEGER DEFAULT 0,
  created_at INTEGER, created_by TEXT
);
```

**ดัชนีที่ต้องมี:** `tour_points(project_id)` · `tour_links(project_id, from_point)` · `tour_versions(project_id, status)` · `tour_shots(version_id, point_id)` · `tour_shots(project_id, point_id)` · `tour_pins(project_id, point_id)`

## 5. โกดังไฟล์ R2

```
<project_id>/tour/plans/<plan_id>.jpg
<project_id>/tour/<version_id>/<point_id>.jpg
<project_id>/tour/<version_id>/<point_id>__<ts>.jpg   ← ของเก่าตอนถ่ายทับ (ถังขยะ)
```

เสิร์ฟผ่าน `GET /media/<key>` (มี CORS อยู่แล้ว) — frontend ประกอบ URL เอง: `CF_API_URL + shot.url`

## 6. สัญญา API (`cf-api/src/modules/tour.ts`)

เส้นทางเดิมของระบบ: `?action=xxx` → เช็คสิทธิ์ → ตอบ `{ ok: true, data: {...} }`

> ⚠️ **ห้ามตั้ง param ชื่อ `action`** (ชนกับชื่อ route → CF ตอบ Unknown action)
> ⚠️ คำสั่งเขียนทั้งหมด **ห้ามส่งผ่านช่องทางที่มี retry อัตโนมัติ** — เน็ตสะดุดจะได้ของซ้ำ

### อ่าน (สิทธิ์ READ)

| action | param | คืนอะไร |
|---|---|---|
| `tour_get_config` | `project` | `{ plans[], points[], links[], versions[] }` — ก้อนเดียวจบ ลดจำนวนคำขอบนเน็ตหน้างาน |
| `tour_get_version` | `project`, `version_id` | `{ version, shots[], pins[] }` · `shots[]` มีครบทุกจุดเสมอ — จุดที่เวอร์ชันนี้ยังไม่ถ่าย backend เติมภาพสำรองให้ (**มองย้อนหลังเท่านั้น** ดูกฎทองข้อ 6) พร้อมธง `fallback_from_version` = `{id, name, captured_at}` · ถ้าย้อนหลังแล้วไม่มีภาพเลย ส่ง `shot: null` + `no_image: true` |

### เขียน — ตั้งค่าโครงการ (สิทธิ์ SITECFG)

| action | param |
|---|---|
| `tour_save_plan` | `project`, `floor_label`, ไฟล์รูป, `plan_id?` |
| `tour_save_point` | `project`, `point_id?`, `name`, `plan_id`, `plan_x`, `plan_y`, `sort_order` |
| `tour_delete_point` | `project`, `point_id` |
| `tour_save_link` | `project`, `link_id?`, `from_point`, `to_point`, `yaw`, `pitch`, `label` |
| `tour_delete_link` | `project`, `link_id` |
| `tour_create_version` | `project`, `name`, `note`, `captured_at` |
| `tour_publish_version` | `project`, `version_id` |
| `tour_delete_version` | `project`, `version_id` (→ ถังขยะ 30 วัน) |

### เขียน — งานหน้าไซต์ (สิทธิ์ OPS)

| action | param |
|---|---|
| `tour_upload_shot` | `project`, `version_id`, `point_id`, `kind`, `haov`, `vaov`, `taken_at` + **ไฟล์ดิบ** |
| `tour_update_shot` | `project`, `shot_id`, `yaw_offset?`, `haov?`, `vaov?` |
| `tour_delete_shot` | `project`, `shot_id` |
| `tour_save_pin` | `project`, `pin_id?`, `point_id`, `version_id?`, `yaw`, `pitch`, `kind`, `ref_id`, `text` |
| `tour_delete_pin` | `project`, `pin_id` |
| `tour_resolve_pin` | `project`, `pin_id`, `resolved` |

### สิทธิ์ (ใช้ระดับที่มีอยู่แล้ว ไม่สร้างใหม่)

| ทำอะไร | ต้องมี | ใครได้ |
|---|---|---|
| ดูทัวร์ | `READ` | ทุกคนในโครงการ (เฟส 1 ปิดฝั่งเจ้าบ้าน) |
| ถ่าย/อัป/ปักหมุด | `OPS` | โฟร์แมนขึ้นไป |
| วางจุด+ลูกศร, สร้าง/เผยแพร่เวอร์ชัน | `SITECFG` | วิศวกรไซต์ / PM ขึ้นไป |

## 7. เรื่องไฟล์ภาพ

### รองรับ 3 ชนิดในตัวเล่นเดียว — ระบบเดาจากสัดส่วนภาพ

| สัดส่วน (กว้าง÷สูง) | `kind` | ค่าเริ่มต้น | ผลตอนดู |
|---|---|---|---|
| 1.8 – 2.2 | `sphere` | haov 360 · vaov 180 | ส่ายได้รอบตัว บน-ล่าง |
| > 2.5 | `pano` | haov ≈ อัตราส่วน × 60 (จำกัด ≤ 300) · vaov 60 | ส่ายซ้าย-ขวาได้ |
| นอกเหนือจากนี้ | `flat` | — | ดูนิ่ง แต่ลูกศรเดินยังใช้ได้ |

ผู้ใช้แก้ `kind` / `haov` เองได้ทีหลัง (บางภาพเดาผิด)

### ตัวสแกน 360 ในแอป (`js/pano-capture.js`) — เจ้าของงานเคาะ 2026-08-18

ไม่ต้องพึ่งแอปนอกที่เสียเงิน · ขั้นตอนใช้งานเหมือน Teleport 360 (จุดไล่เล็ง → เก็บภาพอัตโนมัติ → ต่อเป็น 360)

**หลักการ:** เว็บเข้าถึงได้แค่เซ็นเซอร์หมุน (ไม่มี ARKit) → ใช้ "องศาที่เครื่องหันอยู่" วางภาพลงผืนผ้า 360 โดยตรง
ไม่ได้จับคู่จุดเด่นในภาพแบบแอปเนทีฟ ⇒ **ของไกลต่อเนียน · ของใกล้ตัว (ขอบตู้) จะเห็นรอยต่อ**

| ค่า | ตั้งไว้ | เหตุผล |
|---|---|---|
| ผืนผ้าออก | 3072×1536 (2:1 เป๊ะ) | ตรงนิยาม equirectangular · ระบบจึงอ่านเป็น 360 เต็มลูกอัตโนมัติ |
| จุดไล่เล็ง | ~23 จุด (วงละติจูด 0, ±39°, ±78°) | ซ้อนกัน ~20% ทั้งสองแกน — ห่างกว่านี้เกิด "รูโหว่รูปตา" ตรงมุมที่ 4 ใบบรรจบ |
| มุมกล้องด้านยาว | 63° (ปรับได้ เก็บใน localStorage) | เว็บอ่านมุมกล้องจริงไม่ได้ → ให้ปรับเองครั้งเดียวต่อเครื่อง |
| เก็บภาพเมื่อ | เล็งใกล้จุดเป้า ≤7° | อัตโนมัติ ไม่ต้องกดชัตเตอร์ |

**ทดสอบไป-กลับแล้ว** (สร้างภาพ 360 ต้นแบบ → ตัดเป็นภาพกล้อง → ต่อกลับ → เทียบ):
คลาดเคลื่อนเฉลี่ย 0.8/255 (0.3%) · ไม่มีพื้นที่โหว่ · ต่อภาพ 4.7 วินาที

⚠️ **ข้อจำกัดที่แก้ไม่ได้:** ตั้งแต่ iOS 18 กล้องใช้ไม่ได้ใน PWA ที่ติดตั้งลงหน้าจอ → ต้องเปิดหน้านี้ใน Safari
โค้ดตรวจแล้วเตือนพร้อมบอกทางออก และยังมีปุ่มเลือกรูปจากคลังภาพเป็นทางสำรองเสมอ

### ตัวเล่น
**Pannellum** (MIT · ~90 KB) วางใน `vendor/pannellum/` แบบเดียวกับ lucide — **ห้ามดึงจาก CDN**
รองรับครบทั้ง equirectangular เต็มใบ · พาโนบางส่วน (`haov`/`vaov`) · hotspot

### อัปโหลด
- **บีบอัดที่มือถือก่อนส่ง:** ย่อด้านยาวเหลือ 4096 px คุณภาพ 82% → ~0.8–1.5 MB/ใบ
- **ส่งเป็น base64 ผ่านเส้นทาง `?action=` เดิม** (ตอนสร้างจริงเปลี่ยนจากแผนเดิมที่จะทำทางด่วนไฟล์ดิบ)
  เหตุผล: หลังบีบอัดแล้วไฟล์ ~1.2 MB → base64 ~1.6 MB ซึ่ง Worker รับสบาย
  ส่วนทางด่วนไฟล์ดิบต้องเขียนชั้นตรวจสิทธิ์ขึ้นมาใหม่นอกเส้นทาง `authorize()` เดิม = เพิ่มความเสี่ยงเรื่องสิทธิ์
  โดยแลกกับที่ประหยัดได้แค่ ~400 KB → **ไม่คุ้ม** เลือกใช้เส้นทางเดียวกับการอัปรูปทุกที่ในระบบ
- อ่านเวลาถ่ายจริงจาก EXIF ถ้ามี → ใช้ **เดาเบื้องต้น** ว่ารูปไหนคู่กับจุดไหน
  ⚠️ **ห้ามพึ่ง EXIF อย่างเดียว** — รูปที่ผ่าน LINE มาก่อน EXIF หายเกลี้ยง และช่างถ่ายข้ามลำดับเป็นเรื่องปกติ (ห้องนี้ยังไม่เสร็จ ข้ามไปถ่ายระเบียงก่อน)
  → ต้องมีการ **จับคู่ด้วยมือ (แตะรูป → แตะจุด)** เป็นทางหลักที่ใช้ได้เสมอ ส่วนการเดาเป็นแค่ตัวช่วยกรอกให้ล่วงหน้า ที่ผู้ใช้กวาดตารีวิวจบใน 2 วินาที

### ปริมาณ/ค่าใช้จ่าย
1 โครงการ ≈ 10 จุด × 8 เวอร์ชัน × 1.2 MB ≈ **100 MB**
R2 ฟรี 10 GB → ทำได้ ~100 โครงการก่อนเสียเงิน · เกินแล้วประมาณ 0.50 บาท/GB/เดือน · **ค่าโหลดออกฟรี**

## 8. ลำดับสร้าง

| ก้อน | ได้อะไร |
|---|---|
| **1. แกนกลาง** | 6 ตาราง + ทางด่วนอัปไฟล์ + วางจุด/ลูกศร + ตัวเล่น + เดินด้วยลูกศร + แผนผังจิ๋ว |

## 9. ข้อจำกัดที่รู้ตั้งแต่ต้น (อย่าไปสัญญากับใครว่าทำได้)

1. **ไม่ไหลลื่นเหมือน Google Street View** — กดลูกศรแล้วจะเป็นการตัดภาพไปอีกจุด ไม่ใช่เดินไหลไป (ของจริงต้องใช้กล้องระดับ Matterport หลักแสน)
2. **พาโนมือถือถ่ายในห้องแคบจะบิด** — แก้ในซอฟต์แวร์ไม่ได้ ต้องยืนกลางห้อง
3. **ความสม่ำเสมอสำคัญกว่าความสวย** — ยืนคนละที่ทุกเวอร์ชัน = เทียบไม่ได้ แนะนำ **แปะเทปกาวบนพื้นจริงที่ไซต์ตรงจุดถ่าย**
4. **งานที่เพิ่มให้พนักงานต้องไม่เกิน ~2 นาที/เวอร์ชัน** ถ้าเกิน 5 นาทีเมื่อไหร่ = ดีไซน์ผิดทาง (พนักงานเหนื่อยมากอยู่แล้ว)
